Architecture Overview

The system is a layered client–server web application (see DD-1). The browser UI (C1) talks only to the API Gateway (C2). Behind the gateway, application services handle accounts (C3), characters and parties (C4), progression and rewards (C5), and stats (C6). Both calculation components read game rules through the Game Data Adapter (C7), so no component contains game-specific code. All data lives in one database (C8), and a background service (C9) checks data integrity and manages backups.

Each component below lists the requirements it satisfies. The full mapping is on the Traceability page.

Component Details

C1 Web UI (Presentation Layer)

The UI has four screens. The Login Screen handles sign-in, account creation, and account recovery. The Home Screen lets the user select a game. The Progress Screen adds, finds, updates, and deletes characters, shows the character summary, and shows rewards at each level. The Profile Screen lets the user delete their account. Each screen calls the API Gateway (C2) and never talks to a service directly.

Requirements: FR-1, FR-2, FR-3, FR-4 (4.1–4.6), FR-5, FR-6, FR-7, NF-4.1–NF-4.4

C2 API Gateway & Authentication

The Login API is the single place where requests are authenticated. signIn is public; authenticate is internal and verifies the credentials against the stored password hash. After sign-in, the gateway validates the session on every request and passes a verified user ID to the services behind it (see DD-7).

Requirements: FR-1, NF-1, NF-2, NF-5.1, NF-5.2

C3 Account Manager

The Account API creates accounts, recovers a forgotten username or password by email, and permanently deletes an account and all of its data (FR-9). Before any change, it confirms that the account belongs to the signed-in user.

Requirements: FR-1, FR-9, NF-3, NF-5.2

C4 Character & Party Manager

The Character Management API lets a user select a game and add, find, update, and delete characters. updateCharacter is the manual entry point for level and EXP (FR-3); values are validated against the game definition through C7 before they are saved (DD-8). Ownership is checked on every read and write.

Requirements: FR-2, FR-3, FR-5, FR-6, FR-9, NF-5.2, NF-9

C5 Progression & Rewards Engine

This component works out what a character needs to level up and what the character gains by doing so: the EXP and materials required, the rewards, the equipment and locations that unlock, and the totals from the current level to a target level.

Design element DE-5: progression models (Strategy pattern)

The games we support do not all progress in the same way. In some games only characters have a level. In others the account has a level that unlocks content for every character. In others a single character has its own ladder, such as a bond level. The calculations are the same for each: find the EXP needed for a level and add up the EXP and materials over a range of levels. Only finding which ladder applies to a character differs. We therefore chose an object-oriented design in which each way of finding a ladder is an object behind a common interface, known as the Strategy pattern.

  • ProgressionModelRegistry reads the scope of each track in the game data and hands the work to the matching TrackResolver.
  • TrackResolver is an interface implemented by AccountTrackResolver, CharacterTrackResolver, and CharacterSpecificTrackResolver. Each returns a ResolvedTrack, which describes a ladder in the same form no matter which model produced it.
  • LevelExpEngine checks the level and EXP entered by the player, calculates the EXP remaining and the progress toward the next level, finds the materials for the next level, and totals EXP and materials up to a target level. It runs the same calculation for each member of a party.

LevelExpEngine only works with a ResolvedTrack, so a new progression model can be added without changing it. A target level at or below the current level, or above the level cap, is rejected.

Design element DE-6: rewards and unlocks

Each time a character levels up, the game grants rewards: currency, stat increases, items, equipment, and access to locations. Rewards are looked up in the game data, not calculated.

  • RewardResolver looks up the rewards for a level or a range of levels. Each reward has a type, a name, lore text, and a text description of its image. Equipment and location rewards also act as the unlock rules for a level. For a range of levels, it adds up currency and stat bonuses and lists each unlocked item and location once.

Future extension: the class diagram also shows a RewardTrackEngine for battle passes (tiers with their own XP, free and premium reward lanes, and a season end date). Battle passes are not part of the current requirements, so this class is outside the current scope. Because it reuses LevelExpEngine and RewardResolver unchanged, it can be added later without modifying them.

Requirements: FR-4, FR-4.1, FR-4.2, FR-4.3, FR-4.5, FR-4.6, FR-6, FR-7, NF-2

C6 Stat Calculator

The Stat Calculator computes the stats of a character at a given level and compares those stats before and after a level-up. The stats take into account the character's equipped items and any multipliers that apply.

Design element DE-4: stat pipeline (Pipe-and-Filter)

A stat value starts as a base value for the character's level. Flat bonuses are added, percentage bonuses are applied together, and multipliers are applied. The result is rounded once at the end. Each step takes the value from the step before it, changes it, and passes it on, which is the Pipe-and-Filter architectural style. Games apply these steps in different orders, so the order of the filters for each stat comes from the game's data, not from code.

Problem elementStat calculationLevel-up comparison
Problem definitionReceives a character, a level, and the equipped items and produces the value of each stat.Runs the stat calculation for the current level and the next level and reports the difference.
InputThe base value for the level and the modifiers from equipped items, set bonuses, and multipliers.The same modifiers and the two levels to compare.
FiltersFlat, additive percent, multiplier, and rounding filters, in the order set by the game.The same filters, run once for each level.
OutputThe rounded value of each stat.The value before, the value after, the difference, and the source of each modifier.

Example (Figure 7): the player wants to know what a level-up from 40 to 41 does to a character's attack. The base value at level 40 is 500. The flat filter adds 120 from a weapon to give 620. The additive percent filter adds a 20% set bonus and a 10% passive and applies the total once, giving 806. The multiplier filter applies 1.25 to give 1007.5, and the rounding filter rounds down to 1007. The same pipeline gives 1023 at level 41, so the player sees attack go from 1007 to 1023 (+16), along with the source of each bonus.

  • StatCalculator calculates stats and compares stats at two levels.
  • ModifierResolver turns equipped items, set bonuses, and multipliers into one set of modifiers, each keeping the name of its source.
  • StatPipeline holds the filters for one stat in the order set by the game and passes the value through them. FlatFilter, AdditivePercentFilter, MultiplierFilter, and RoundingFilter each encapsulate one step.
  • StatComparison holds the result: the stat, the value before, the value after, the difference, and the sources.

When a comparison is requested, StatCalculator asks ModifierResolver for the character's modifiers, passes each stat's base value at the current level through StatPipeline, then does the same for the next level with the same modifiers, so only the level changes. It returns the results in a StatComparison.

Requirements: FR-4, FR-4.4, FR-7, NF-2

C7 Game Data Adapter

Games store their data in different shapes. The Game Data Adapter applies the Adapter pattern: the client works only with ClientGameDataInterface, and GameDataAdaptor implements it by transforming each game's raw data into one common GameCharacter model (EXP, level materials, rewards, before/after stats, new equipment and items, and new locations). The rest of the system never needs to know which game the data came from (DD-3).

Requirements: FR-2, FR-3, FR-4.1–FR-4.6, FR-5, FR-8, NF-2, NF-6, NF-7, NF-8

C8 Database (User Data + Game Definitions)

A User (with a hashed password) has many Characters; each character belongs to one Game. Each game owns its definition data: Game_Items and Game_Locations (each with the level that unlocks it), Game_Materials, and Game_Stat_Increases (a level formula per stat and class). Because game rules are rows of data rather than code, a new game is added by inserting data (FR-8, NF-7).

Requirements: FR-1, FR-2, FR-3, FR-5, FR-8, FR-9, NF-1, NF-3, NF-5.1, NF-6, NF-7, NF-9, NF-10

C9 Data Integrity & Backup Service

All writes pass through the Data Verifier, which checks that the input has the right structure and that the request is authorized before writing to the database. verifyDatabaseIntegrity runs the scheduled reference checks on stored data (NF-8). The same service manages backups and restore (NF-10, DD-9).

Requirements: FR-9, NF-1, NF-8, NF-10
