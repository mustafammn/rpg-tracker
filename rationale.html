The RPG Character Progression Tracker has one core difficulty. It must present one consistent, consolidated view of progression for many RPGs whose progression rules differ widely. Some games level each character separately. Some level the whole account. Some use both, and every game has its own EXP curves, materials, stat formulas, and unlocks. Most of the decisions below follow from treating that variation as data, not as code. The remaining decisions cover persistence, security, scale, and accessibility.

Each decision lists the requirements that drive it, the alternatives we considered, the option we chose and why, and the costs we accepted. Component IDs (C1–C9) refer to the High-Level Design. The Traceability Matrix gives the full mapping from requirements to components.

DD-1 Layered Client–Server Web Application

Driving requirements: FR-9 (data available across sessions and devices), NF-1 (99% availability), NF-2 (200 concurrent users), NF-4.2 and NF-4.3 (works across browsers and devices).

Alternatives considered: (a) a native desktop or mobile application with local storage; (b) a thick client that syncs to a cloud store; (c) a layered web application with a thin browser client.

Decision. The system is a layered web application. Its layers are presentation (C1), an API gateway (C2), application services (C3–C7, C9), and persistence (C8). Each layer calls only the layer directly below it.

Justification. FR-9 requires the same characters and parties on every device a user signs in from. With a local-storage client (a), that requirement turns into a synchronization problem, including conflict resolution when two devices edit the same character offline. A thick syncing client (b) solves FR-9, but it duplicates the game rules on every platform, and every platform would need an update whenever a game is added. That conflicts with NF-7. A browser client served from one backend meets NF-4.2 and NF-4.3 with one code base. It also keeps all game rules and user data in one authoritative place. Layering lets the application services stay stateless (see DD-4), so we can add servers behind a load balancer to meet NF-2 and keep the system running when one server fails (NF-1).

Trade-offs. The tracker needs a network connection to work. We accept this because users check progression while they are already online to play. Each request also crosses several layers, which adds latency. DD-5 addresses that cost.

DD-2 Game Progression Rules Stored as Data, Not Code

Driving requirements: FR-8 (games stored as data that defines progression mechanics), NF-6 (at least 200 games), NF-7 (add games without major changes to existing data or application logic).

Alternatives considered: (a) one hard-coded module per game; (b) a plug-in architecture with one compiled plug-in per game; (c) a declarative game definition, interpreted by generic code.

Decision. Each supported game is described by a game definition. This is a structured document holding the game's level caps, EXP curve (as a table or a formula), stat growth tables, materials per level, rewards per level, equipment and location unlocks, and the game's progression model and party rules. Definitions are stored in C8. The application code reads them but never contains game-specific logic.

Justification. With 200 or more games (NF-6), options (a) and (b) mean writing, testing, and deploying 200 code modules. Adding a game would be a code change and a release, which is what NF-7 rules out. Plug-ins (b) isolate games from each other better than (a), but they still need developers for every new title. A declarative definition (c) is the most direct reading of FR-8. It turns "add a game" into a data-entry task, and it lets us check a game's data with a schema validator before it goes live. Game designers already publish progression as tables (EXP per level, materials per ascension), and those tables map naturally onto this format.

Trade-offs. A data format cannot express every possible rule. A game with very unusual mechanics may need a schema extension. We limit this risk with DD-3: the format allows several progression models, and the adapter is the only place that has to change when a new model appears.

DD-3 A Game Data Adapter Normalizes All Progression Models

Driving requirements: FR-8 (level-based, account-wide, and character-specific models), FR-3 (account-level progression where the game defines it), FR-4 (one consistent view for every game), FR-5 (parties only in games that support them), NF-7.

Alternatives considered: (a) give the calculation components a branch for each progression model; (b) put an adapter between the stored definitions and the rest of the system.

Decision. The Game Data Adapter (C7) reads a raw game definition and presents it to the rest of the system through one internal interface. The interface answers four kinds of questions: what is required to go from level n to n+1 for this progression track, what is granted at level n, which stats change at level n, and what this game supports (parties, account levels, level caps). Each of a character's progression tracks, and the account's own track where the game has one, is exposed as a track with the same shape.

Justification. If the Progression Engine (C5) and Stat Calculator (C6) branched on progression model (a), every new model would require edits to both, and every combination of models would need its own tests. The adapter follows the Adapter pattern. It confines model-specific knowledge to one component, so C5 and C6 can work with any game. FR-4 asks for a single consolidated view whatever the game. The adapter is what makes that possible, because C1 always receives the same structure. It also answers FR-5's "for games that support parties": C4 and C1 ask the adapter whether to allow and display parties, so they never check which game it is.

Trade-offs. The adapter adds a layer of indirection, and its interface has to be designed with care. A poor interface would leak game-specific detail into C5 and C6. The adapter also caches parsed definitions, because definitions are read constantly and change rarely. This supports NF-2.

DD-4 Stateless, Separate Calculation Components

Driving requirements: FR-4.1–FR-4.6 (consolidated per-character view), FR-6 (party summary), FR-7 (cumulative totals up to a target level), NF-2 (200 concurrent users).

Alternatives considered: (a) precompute every character's view and store it in the database; (b) compute on demand in one combined service; (c) compute on demand in two separate stateless components.

Decision. Two stateless components compute progression results on demand from (character state, game definition). The Progression and Rewards Engine (C5) computes EXP, materials, rewards, and equipment and location unlocks. The Stat Calculator (C6) computes before-and-after stats and their differences.

Justification. Precomputing (a) looks fast, but stored results would go stale whenever a user edits a level (FR-3) or a game definition is corrected (NF-8). We would then need cache-invalidation logic across thousands of characters. The calculations themselves are inexpensive: table lookups and short sums over at most a few hundred levels. Computing on demand is therefore fast enough and always correct. We separated stat calculation from progression (c instead of b) because the two change for different reasons. Stat formulas are the most game-specific and most complex part of a definition (base values, growth rates, multipliers). Rewards and unlocks are simple lookups. Separating them keeps each component cohesive and lets each be tested on its own. FR-7 reuses the same functions: the cumulative view folds the single-level calculation over the range from the current level to the target. Because both components hold no session state, any server can handle any request, which makes horizontal scaling for NF-2 straightforward.

Trade-offs. Some work is repeated across requests. The cached definitions from DD-3 and the small size of each calculation keep that cost low.

DD-5 One Aggregated Endpoint for Each Consolidated View

Driving requirements: FR-4 (one consolidated view), FR-6 (party summary), FR-7 (target-level totals), NF-2.

Alternatives considered: (a) fine-grained REST endpoints, which the browser calls separately for EXP, materials, rewards, stats, and unlocks, then combines; (b) one aggregated endpoint per view, assembled on the server.

Decision. The gateway (C2) exposes one endpoint for each view: character view, party summary, and target-level plan. Each request calls C5 and C6 on the server and returns one combined response to C1.

Justification. FR-4's main promise is that the user no longer has to look across several screens. Option (a) would just move that scattering into the client. Showing one character would take five or more network calls, and a six-member party summary (FR-6) would take thirty. Under 200 concurrent users (NF-2), that request volume dominates load. It also hurts users on mobile networks, who matter for NF-4.3. Server-side aggregation keeps the client simple and the response consistent, since every part is computed from the same snapshot of the character. It also gives C1 a single, stable contract to render.

Trade-offs. An aggregated response can include data a particular screen does not show. We accept slightly larger responses in exchange for fewer round trips and a simpler client.

DD-6 Relational Database with Transactions; Game Definitions as Versioned Documents

Driving requirements: FR-9 (persist accounts, characters, parties, and progression), NF-3 (5,000 users), NF-6 (200 games), NF-9 (no race conditions in database transactions).

Alternatives considered: (a) a pure document (NoSQL) store for everything; (b) a fully normalized relational schema for everything, with every game rule as rows; (c) a relational store for user data plus versioned JSON documents for game definitions, in the same database.

Decision. User data (accounts, game memberships, characters, parties, party members, progression records) lives in relational tables with foreign keys and ACID transactions. Each game definition is stored as a versioned JSON document in the same database, keyed by game ID and version.

Justification. User data is highly relational. A party belongs to an account and references characters, and each character references a game. Deleting an account (FR-9) must remove all of these together. Foreign keys with cascading deletes and transactions handle this correctly. Transactions with row-level locking or optimistic version checks also meet NF-9. For example, two devices updating the same character's level at once cannot silently overwrite each other. Game definitions are different. Their shape varies from game to game, and they are read as a whole. Forcing every game into a fixed normalized schema (b) would undo the flexibility of DD-2. Storing them as documents (c) keeps that flexibility. Version numbers let a corrected definition (NF-8) be published without changing history, and let a bad update be rolled back. The data volume involved (5,000 users and 200 games) is small for a single relational database. So NF-3 and NF-6 can be met without sharding, and adding a read replica later is simple.

Trade-offs. The database must check the internal structure of definition documents at write time, because the relational schema does not enforce it. C7 and C9 perform this check against a definition schema (see DD-9).

DD-7 Authentication at One Gateway, Ownership Checks, and Encryption

Driving requirements: FR-1 (accounts, sign-in, sign-out), NF-5.1 (encrypt sensitive data), NF-5.2 (prevent unauthorized access to private progression data).

Alternatives considered: (a) each service authenticates requests itself; (b) one gateway authenticates every request, and the domain services check ownership.

Decision. C2 terminates TLS, validates the session token on every request, and passes a verified user ID to the services behind it. C3 and C4 confirm that the requested account, character, or party belongs to that user before any read or write. Passwords are stored only as salted, slow hashes. The database and its backups are encrypted at rest.

Justification. Putting authentication in one place (b) means no endpoint can be accidentally left unprotected. With approach (a), every new service is another chance to forget a check. Authentication alone does not meet NF-5.2, though. A signed-in user who changes a character ID in a request must still be refused. That is why the ownership check sits in the components that own the data. Encryption in transit and at rest, plus password hashing, means a compromised disk or backup does not expose account data. This is the "in case the system is compromised" scenario in NF-5.1.

Trade-offs. Encryption and hashing add a small CPU cost to sign-in and storage. This is negligible at the scale in NF-2 and NF-3.

DD-8 Manual Progress Entry, Validated Against the Game Definition

Driving requirements: FR-3 (manually enter and update level, EXP, and account progression), NF-8 (displayed progression stays accurate).

Alternatives considered: (a) import progress automatically through game publisher APIs; (b) manual entry with no validation; (c) manual entry validated through the adapter.

Decision. Users enter their level and EXP by hand, as FR-3 specifies. Before C4 saves the values, it uses C7 to confirm that the level is within the game's cap and that the EXP is within the range for that level.

Justification. Few RPG publishers offer public progression APIs, and those that do differ completely. Building on them (a) would make the system depend on third parties and break NF-7. Manual entry works for every game. Without validation (b), though, one typo (level 900 in a game capped at 90) would produce a nonsense consolidated view. Validating through the adapter keeps the check generic, because the cap and EXP range come from the definition, so no game-specific code is needed.

Trade-offs. Users must keep their own numbers up to date. The architecture leaves room to change this later (see Design Evolution).

DD-9 Separate Integrity and Backup Service

Driving requirements: NF-8 (regular reference checks), NF-10 (backups and restore), NF-1 (availability), FR-9 (permanent deletion of an account and all associated data).

Alternatives considered: (a) run checks and backups inside the request-handling services; (b) a separate background service.

Decision. The Data Integrity and Backup Service (C9) runs on a schedule, outside the request path. It (1) checks every game definition against the definition schema and for broken references, such as a reward that names an item no longer defined or an EXP curve that does not increase, and flags problems for maintainers; (2) takes regular database snapshots plus continuous transaction logs for point-in-time restore; and (3) expires backups on a fixed retention window, so that data from a deleted account cannot remain in backups indefinitely.

Justification. NF-8 and NF-10 are periodic maintenance tasks. Running them in the request path (a) would slow user requests and couple maintenance to traffic, which works against NF-1 and NF-2. A separate service can run at low-traffic times and fail without affecting users. FR-9 and NF-10 pull in opposite directions: deletion must be permanent, but backups exist to keep data. A fixed retention window resolves this. A deleted account is removed from the live database at once and disappears from every backup once the window expires. We state this policy openly on the account-deletion screen.

Trade-offs. One more component to deploy and monitor. Restoring from a backup taken before a deletion could bring the deleted account back, so C9 keeps a deletion log and re-applies it after any restore.

DD-10 Responsive, Semantic, Accessibility-First UI

Driving requirements: NF-4.1 (screen readers and text alternatives), NF-4.2 (cross-browser), NF-4.3 (cross-device), NF-4.4 (color contrast).

Alternatives considered: (a) a canvas-heavy, game-styled interface; (b) semantic HTML with responsive layout, where every chart is backed by a data table.

Decision. C1 is built from standard semantic HTML elements and ARIA labels, using a single responsive layout. Every chart (EXP progress, stat comparison) is generated from the same structured data as an accessible table, and every icon and item image has a text label. The color palette is checked against WCAG AA contrast ratios.

Justification. A canvas-based interface (a) is opaque to screen readers, so NF-4.1 would have to be retrofitted for every view. Since DD-5 already delivers plain structured data, C1 can render both a visual and a textual version of each view at little extra cost. Standard HTML and CSS work in all current browsers (NF-4.2). One responsive layout serves phones and desktops (NF-4.3) without a separate mobile application.

Trade-offs. The interface is less visually immersive than a game-styled one. We judged correctness and access more important for a reference tool.

Design Evolution

We evaluated the design against the changes we consider most likely after launch. For each one, the table names the components that would change.

Likely changeImpact on the design
A new game is releasedAdd a new game definition to C8. C9 validates it. No code changes (DD-2, NF-7).
A game introduces a new kind of progression (e.g., a skill tree or prestige resets)Extend the definition schema and the adapter (C7) only. C5, C6, and C1 continue to consume the same track interface (DD-3).
A game patch changes its EXP curve or rewardsPublish a new version of the definition. C9's reference checks catch inconsistencies (DD-6, DD-9, NF-8).
A publisher releases a progression APIAdd an importer behind C4 that writes the same validated progress records that manual entry produces. The rest of the system is unchanged (DD-8).
A native mobile app is requestedThe app consumes the same aggregated endpoints from C2. No backend changes (DD-1, DD-5).
User growth well beyond NF-2 and NF-3Add stateless service instances and a database read replica. No change to component boundaries (DD-1, DD-4, DD-6).

Summary

The central decision is to treat game rules as data (DD-2) behind a single adapter (DD-3). That decision is what lets one generic set of calculation components (DD-4) produce a single consolidated view (DD-5) for any number of very different RPGs. The remaining decisions keep that core reliable, secure, and accessible. They provide transactional user data (DD-6), centralized authentication with ownership checks (DD-7), validated input (DD-8), background integrity checks and backups (DD-9), and an accessible interface (DD-10). Every decision is traced to one or more requirements, and the components most likely to change are isolated so that change stays local.
